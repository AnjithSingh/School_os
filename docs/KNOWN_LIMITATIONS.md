# Known limitations

These are deliberate v1 boundaries, not hidden bugs. Anything here should be
planned as a milestone rather than patched in ad hoc.

## Scope and tenancy

- **Single school only.** Tenant tables already carry `school_id`, but there is
  no school switcher, per-school branding beyond stored colours, or row-level
  school isolation enforced by a global query filter.
- **Classes 6-10 only.** The schema allows other levels; the UI and seed data
  target the Indian middle/high-school range.
- Sections are recreated per academic session; historical sections remain
  readable but there is no cross-session section merge tool.

## Results

- Results are computed **per exam**, not as a term aggregate. Term weighting
  (for example FA1 + FA2 + SA1) is deferred.
- Report card layout is a single template version (`v1`). Schools cannot yet
  upload custom templates.
- Grade bands are configurable but assume non-overlapping ranges. Fractional
  percentages inside integer-band gaps fall to the nearest lower band by
  design (for example 32.9 falls in the 0-32 band).

## Fees

- Online payment gateways are not integrated. Payments are recorded manually
  (cash, cheque, bank transfer, offline UPI) and receipts are generated locally.
- Concessions are approved by staff; there is no parent-facing concession
  request workflow.
- Refunds are modelled as payment reversals plus adjustments, not as a full
  refund approval chain.

## Communication

- Announcements are one-way. Free-form parent-teacher messaging is deferred.
- Notifications are in-app only; email and SMS delivery are not wired up.
- Homework submissions are file/text based with staff review; there is no
  plagiarism or rubric engine.

## Authentication

- Student login is password-first. An optional PIN quick-login is deferred.
- Password reset tokens are generated by staff; self-service email reset is not
  configured because the app does not yet send mail.
- Two-factor authentication is not implemented.
- Login throttling and account lockout are per account, not per IP/device.

## Operations

- SQLite is the only supported database. The SQLAlchemy layer is portable, but
  PostgreSQL has not been exercised.
- There is no background worker. PDF generation, backups and any bulk operation
  run inside the request or CLI command.
- Backups are on-demand CLI commands; scheduling and off-site replication are
  the operator's responsibility.
- Logging goes to files under `instance/logs`; there is no log shipping,
  metrics endpoint or alerting.
- File storage is local disk. There is no object-storage adapter or virus scan
  on uploads.

## Accessibility and UI

- The design system targets WCAG AA colour contrast and keyboard use, but no
  formal audit has been run with assistive technology.
- Charts are canvas-based with textual summaries nearby; screen-reader access
  to the charts themselves is limited.
- The UI is English-only and not localised.

## Testing

- The suite covers services, permissions and key routes; it is not exhaustive
  for every admin CRUD screen.
- Tests run on in-memory SQLite, so database-specific behaviour (for example
  PostgreSQL constraints or concurrency) is not covered.
- There is no browser end-to-end suite; responsive and print layouts were
  checked manually.
